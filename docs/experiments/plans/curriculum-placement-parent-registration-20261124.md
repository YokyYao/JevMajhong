# Retained-parent placement registration

The explicit registration adapter consumes only the qualified retained3B seal
and completed full57-source materialized corpus. It names the retained25 replay
and normalized-terminal child loss in the actual training configuration and
registration. No flag silently relabels an old-loss training configuration.

The original registration function code object is reused in an isolated global
namespace. Its actual data hashes, TRAIN membership/fingerprint, current
validation membership, two epoch orders, inherited Qwen/runtime identities,
reference policies, new optimizer and immutable source bindings remain in force.
The numeric recipe checker receives a derived loss-name view; all counts,
weights, caps, masses, budgets and schedules remain unchanged. Parent validation
uses the separately implemented retained-parent verifier and genuine exits.

The final registration write adds explicit retained/normalized-alignment markers
and runs the existing retained-placement runtime contract. A mismatch between
the actual training loss and curriculum loss is rejected. No source module
globals are patched, and neither an existing registration nor fit is replaced.

The new run has a separate output directory. Its budget is still derived from
the actual completed two-epoch exposure corpus, with fresh64 baseline/final
matches and identical16-cell curves. A registration alone never admits fit;
full serving validation, exact inherited tensors, early-input parity and the
original development criteria still require a bound prelaunch integration.

Software preflight freezes this adapter and verifies the actual future parent
is still unavailable. It does not create an actual registration, seal or model,
and does not submit a job. All preparation requires a finite scheduler GPU
allocation. Raw records stay private; only source and aggregates are published.
