# 为什么桌面模型几乎不吃不碰：已复现训练候选泄漏

结论：桌面端发送两张自己手牌作为吃/碰的 `consumed` 是正确的实时动作格式。当前权重对该格式几乎总选跳过。根因至少包含旧训练回放候选的答案泄漏，不能通过把桌面动作改成错误的三张来修复。已修复新数据生成入口并加入回归检查，**没有训练或替换现有权重**；已有模型仍需要使用正确候选重新训练/修复。

## 一、同一权重、同一局面的输入对照

使用本机部署的校正版2、RiichiEnv 0.4.11，从8个隔离牌山生成合法实时反应，确定性选取24个未标注场景。仅改变请求字段，不改变权重、手牌或候选动作种类。公开汇总见 [summary.json](https://github.com/YokyYao/JevMajhong/blob/4bdbd79c39071fb523f79bbe1079303c13770a65/reports/2026-11-09-call-policy-diagnosis/summary.json)。

| 输入版本 | 跳过次数 / 24 | 平均跳过偏好 |
| --- | ---: | ---: |
| 完整原生实时输入 | 24 | 0.999531 |
| 时序字段设为未知 | 24 | 0.999525 |
| 时序未知并使用桌面默认分数等信息 | 24 | 0.999913 |
| 时序与牌桌信息均显式未知 | 24 | 0.997925 |
| **仅把吃碰 consumed 改为含来牌的三张** | **0** | **0.000117** |

最后一行是故意模拟坏训练格式的诊断，**不是生产修复方案**。24个场景没有专家正确动作标签，所以这不是24次正确/错误策略判定，也不衡量胜率。它证明模型选择对一个与训练答案相关的格式特征极为敏感，而不是单纯缺少桌面时序导致。

## 二、同一场模拟对局，实时观测与回放观测对照

生成一场同时含吃、碰、跳过的脚本对局，将完全相同的事件交给训练使用的 `MjaiReplay.steps`。比较100个可配对的吃碰反应位置：

- 实时：不论最终选什么，吃和碰候选的 `consumed` 均为两张自己手牌。
- 回放：实际选择吃/碰时，目标候选包含来牌，变成三张；选择跳过时，候选仍是两张。
- 回放还会漏掉未被选中的其他吃法或杠选项。因此仅移除第三张仍不足以修好候选集合。

示例（同一手牌、同一来牌）：

```json
{"live":   {"type":"chi","pai":"6m","consumed":["7m","8m"]},
 "replay": {"type":"chi","pai":"6m","consumed":["6m","7m","8m"]}}
```

这让模型有机会按“候选里含不含第三张”识别训练答案，无需学会鸣牌价值。历史验证集中吃/碰17/17的高一致率不能再当作真实吃碰判断能力的证据；原始历史数据仍需逐条审计，不能把本次脚本对照冒充对全部旧数据的检查。

## 三、已修复的数据入口

`replay_call_repair.py` 与 `prepare_raw.py` 的新流程：

1. 从可见手牌、最近弃牌及来源座位独立重建全部吃/碰候选，不把专家选择传给候选生成函数。
2. 只序列化自己消耗的两张牌，保留赤牌；专家动作仅在候选完成后用于设置标签。
3. 恢复未被选择的合法吃法，并检查上家限制、手牌所有权、食替后仍有合法弃牌。
4. 杠可选、可能荣和、弃牌来源不明等尚未完整重建合法性的状态，明确排除并记录原因，绝不改成“跳过”标签。
5. 新数据标为 `semantic-v2-call-repaired`，记录修复代码 SHA、修复/排除数量，禁止覆盖旧输出目录；同一比赛内也按请求哈希去重。

本次100个配对位置中，83个满足安全重建条件，**83个的修复后候选集合全部与实时引擎一致，补回12个缺失候选**。其余17个明确排除：弃牌来源不明5、涉及杠5、可能荣和7。这是候选表示和合法性回归，不证明强度提升，也不覆盖所有规则边界。

`semantic.py` 的原生实时接口和已部署桌面的正确两张编码没有改动；冻结的历史实验不被静默重新解释。旧训练权重、旧数据文件均未覆盖。

## 复现命令

本次回归共运行45项测试，43项通过，2项因本机缺少历史专家数据而跳过；包含新数据入口端到端生成、候选集合对照和桌面现有回归。

安装根目录依赖（已固定 RiichiEnv 0.4.11）后：

```bash
python -m unittest test_replay_call_repair test_semantic
python desktop/audit_replay_calls.py --out runs/replay-call-audit --policy mixed
python desktop/diagnose_call_policy.py --out runs/call-ablation --seeds 8 --cases 24
# 恢复模型资源、配置本地固定底座并确认 CUDA 后：
python desktop/diagnose_call_policy.py --out runs/call-ablation --evaluate
```

新训练数据应使用新的输出目录执行 `prepare_raw.py`；检查 `provenance.json` 的新 schema、`call_repair_audit`、`call_exclusions` 和代码哈希。不直接延长旧训练计划，不用旧的34条吃碰验证结果选模。先在独立实时/重建反应数据上确认判断有效，再测完整对局的得点、顺位及放铳，最后决定是否替换模型。

未核验截图和脚本对局里的动作均不能当作专家最优标签。此处只诊断和修复数据/接口，服务器训练仍需采用审核过的来源与新的分组验证。
